# gpsfree

GPS-free localisation benchmark for drones. Algorithms get IMU, magnetometer, barometer and a ranging sensor plus
a prior 3D map, and must estimate their position (and say how sure they are) without ever seeing ground truth.
Scored on **12 scenarios × 20 runs**: towns, forests, fields, coast, mountains and desert, mostly in Finland and
Ukraine, with wind, imperfect maps and, in three scenarios, a wrong start position after a spoofed GNSS handover.

## Scenarios

Each scenario (`benchmark/scenarios/<id>.json`) fixes a world, the flight style, the wind, how good the drone's map
is and whether the start is wrong. The **true world** the sensors measure has terrain, buildings and trees; the
**map** the algorithm gets (`ctx.map`) has the terrain with height errors, buildings with roof errors and some
missing, and never any trees. Buildings and forest come from Overture Maps (release pinned in
`gpsfree/worlds/overture.py`, extracts committed in `benchmark/worlds/`), terrain from AWS Terrain Tiles.
Run *i* of a scenario always has the same route, gusts, noise and start offset.

## Scoring rules

- **Error** is the 3D distance between the estimate and the true position, sampled at 10 Hz.
- **Run score**: the mean of log₁₀(error) from 100 m travelled to the end, error clamped to 1 m … 100 km: the
  geometric-mean error along the flight.
- **Scenario score**: the median run score over its 20 runs. **Overall score** (the ranked number): the geometric
  mean of the 12 scenario scores, so every scenario weighs the same whatever its error scale.
- **Robustness** (shown, not ranked): the worst scenario and the share of runs that were ever off by more than
  50 m ("runs lost").
- **Integrity** (shown, not ranked; needs a method that implements `uncertainty()`, the 95% horizontal radius it
  believes it is within, or `inf` for "I don't know"):
  - *misleading*: share of the time the true horizontal error lies outside the reported radius;
  - *silent*: share of runs with hazardously misleading information, i.e. off by more than the 50 m alert limit
    while claiming to be within it. This is the failure that matters most: believing a wrong position.
  - Methods that report nothing show "no claim".
- **Diagnostics** in `results.json`: mean error per distance band, distance when first lost, error growth slope,
  first warning, xy/z RMSE.
- The rules live in `benchmark/suite.json`, `benchmark/scenarios/`, `benchmark/hardware/`, `benchmark/rangers/`,
  the world catalogue and `gpsfree/evaluate.py`. Changing any of them changes the suite fingerprint and marks every
  existing result ⚠ stale until it is re-run.

## Rules for experiments

- **Every number comes from the CI scorer.** An experiment is `experiments/<name>/algo.py` defining
  `Navigator(gpsfree.Algorithm)`, scored with `uv run gpsfree eval <name>`: the exact code CI re-runs. Don't report
  numbers from side scripts with their own metric, noise model or initial conditions. If an idea can't be expressed
  as a `Navigator`, change the harness in a PR so everyone gets it.
- **No ground truth.** A `Navigator` sees only the start pose, sensor callbacks and the prior map.
- **Real hardware.** Set `hardware = "<profile>"` on the `Navigator` to replace the suite's IMU and magnetometer
  with a real part from `benchmark/hardware/<profile>.json`. Leave it unset (`None`) to use the suite's default
  sensors. Profiles store datasheet numbers in datasheet units, with the document revision, table and URL. Any
  number that isn't from a datasheet is marked `ASSUMPTION`. `gpsfree/sensors.py:hardware_sensors` converts them:
  - white noise σ = noise density × √rate;
  - a constant per-run bias drawn from N(0, in-run bias stability);
  - for parts that publish no bias stability, the bias σ is the temperature coefficient × `delta_temp_c`.
- **Ranging sensor.** Set `ranger = "<name>"` to pick a real part from `benchmark/rangers/` (default `tf03`):
  | ranger | part | beams | range on natural ground | price (USD) |
  |---|---|---|---|---|
  | `tf03` | Benewake TF03 laser rangefinder, pointing down | 1 | 100 m | 229 |
  | `mid360` | Livox Mid-360, mounted upside down | 80, ring to 52° below horizon | 40 m | 749* |
  | `avia` | Livox Avia, pointing down | 49, cone ±35° around nadir | 190 m | 2,079 |

  \* ASSUMPTION for the Mid-360: list price, no current official quote found.
- **Hardware under $3,000.** The cost column counts the IMU profile, the magnetometer if the method implements
  `on_mag` and the ranger if it implements `on_echo`. It must be under $3,000; CI fails the PR otherwise and the
  leaderboard leaves it out.
- **Variants reuse code.** Subclass another experiment with `load_algorithm("imu_deadreckoning")` rather than
  copying it. CI only re-verifies experiments a PR touches, so if you change a base, re-run and commit its
  subclasses' `results.json` too.

## Submitting

```sh
uv run gpsfree fetch --suite --missing   # download + bake the suite's worlds into data/worlds (a few minutes once)
uv run gpsfree new my_method             # copy a template into experiments/my_method
uv run gpsfree eval my_method --quick    # 3 runs per scenario while iterating (doesn't write results.json)
uv run gpsfree eval my_method            # the full suite, writes experiments/my_method/results.json
uv run gpsfree replay my_method kyiv     # export a run for the 3D replay app (data/replays)
uv run gpsfree viz                       # results page with runs, scenario matrix and studies (data/viz)
```

1. Commit `experiments/<name>/algo.py` and `results.json`, open a PR.
2. CI re-runs only the experiments the PR touches (240 runs each, budget 7 minutes) and fails if the committed
   `results.json` doesn't reproduce or the hardware costs $3,000 or more. Scoring worse never blocks a merge.
3. After merge, CI regenerates the leaderboard above (top 5 methods) and commits it to `main`. Don't edit it by hand.
